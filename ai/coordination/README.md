# ai/coordination/ —— 协作规则与决策登记

> 上级：[`../README.md`](../README.md) · 对应指南 **3.3.5.3**（设计报告必含「智能体工作流设计」）
> 与 **3.3.5.5**「大模型协作与技能包」（**15 分**）。

本目录回答两个问题：**多个人 / 多个 AI 同时改一个仓库时，怎么不互相覆盖、不各干一套？**
以及 **一个还没定的事，凭什么不能先动手做？**

| 文件 | 谁写 | 规则 |
|---|---|---|
| [`README.md`](README.md) | 本文件 = 协作规则本身；**由用户裁定**，AI 只能提方案 | 规则变更需用户拍板 |
| [`DECISIONS.md`](DECISIONS.md) | **决策裁定后追加** | 三档状态；`discussing` 的决策**任何成员不得据以行动** |

---

## 一、决策登记三档状态

| 状态 | 含义 | **可以做什么** | **不可以做什么** |
|---|---|---|---|
| `discussing` | 讨论中，**用户尚未裁定** | 讨论、记录、写方案文档、做只读调研与可行性核算 | ❌ **不得据以改动 `src/`、`build/`、`board/`** |
| `decided` | **已由用户明确裁定** | 可作为设计依据推进实现 | ❌ 不得单方面推翻；要改须重新登记并注明取代关系 |
| `rejected` | 已被否决 | 记录在案，避免有人第二次提同一个方案 | ❌ 不得再据以行动 |

### ★ 硬规则（本项目最重要的一条协作纪律）

> **`discussing` 的决策不得据以改动 `src/`、`build/`、`board/`** ——
> **只能讨论与记录。**

- 依据：`docs/repo_spec.md` **§7「待定项（由用户裁定，勿擅自填入）」** ——
  指南与仓库骨架已为这些项**预留落点**，但**内容待裁定后再填**。
- **为什么必须写成硬规则而不是态度呼吁**：讨论中的方案一旦落进源码，
  后面「按新裁定重做」的成本会翻倍，而且**分歧会被藏在代码里**，
  评审看到的实现与文档写的方向对不上。
- 允许的「讨论期动作」：只读调研、算术核算（资源 / 带宽 / 时序估算）、
  在 `docs/` 或 `ai/` 下写方案与对比表、给出判据与代价。
  **判据**：这些动作**不改变任何 `src/`、`build/`、`board/` 文件**。

### 状态怎么变

1. 任何成员都可以**提出**（`discussing`）；
2. **只有用户**（或其明确授权的一方）能裁定为 `decided` / `rejected`；
3. 裁定后，由登记人**在 `DECISIONS.md` 原地更新状态并写明依据原文**
   （用户原话或选择项原文 + 日期），**不新建重复条目**；
4. 已登记的条目**不删除**；被推翻的写法是「加注取代指针」，保留原文（可追溯）。

## 二、环境与出处纪律（配合决策使用）

| 纪律 | 说明 | 出处 |
|---|---|---|
| **数字必须标来源** | 正文里任何器件参数、资源占用、时序数字，都要能指回 `docs/repo_spec.md` §6 环境事实表或 `build/reports/` | `docs/repo_spec.md` §6 末注 |
| **本机实测 ≠ 传闻** | 「本机只有 2020.2」这类事实必须来自实际列目录，不是记忆 | 同上 §6「工具链」行 |
| **不擅自填待定项** | 见上方硬规则 | 同上 §7 |
| **不得编造** | 决策、提出方、日期、依据原文一律以**实际发生**为准；宁可写「未记录」，不写看起来完整的内容 | 本目录纪律 |

## 三、协作分工与写范围（Agent Teams）

| 角色 | 谁 | 做什么 |
|---|---|---|
| 裁定 | **用户** | 裁定 `discussing` 项；冲突时最终裁决 |
| 统筹 | **Lead** | 拆任务、定写范围、收口与最终验收 |
| 执行 | 各子任务负责人 | 在**各自的写范围内**产出；跨范围只读 |

- **写范围隔离**：每个子任务声明自己的写范围（如 `ai/`、`docs/`、`build/scripts/`），
  **不越界写别人的路径**；需要别人改，**发消息请求**，不要代笔。
- **唯一事实源**：目录职责冲突以 [`../../docs/repo_spec.md`](../../docs/repo_spec.md) **§2 目录职责表**裁决。
- **本目录的登记权**：`DECISIONS.md` 由**裁定后**追加；同时只有一方在写时**追加行**，不重写全表。

### ★ 子代理使用纪律（2026-10-20 用户裁定）

- **复杂任务或大量琐碎事项**：默认拆给**多个子代理并行**推进，不要串行硬扛。
- **模型选择**：子代理统一选 **`group/1101`**（完整模型 ID：`magpie/group/1101`）。
- **主代理职责**：拆任务、给每个子代理划定写范围、汇总结果并做最终验收；
  子代理只在其写范围内产出，跨范围只读。
- **不强制拆分**：单步任务、强顺序依赖、或拆分后协调成本高于收益的任务，主代理直接做。
- **判据**：拆分必须减少总耗时或降低单点上下文压力；不得为了“多代理”制造重复劳动或写冲突。

## 四、怎么用

```powershell
# 1) 动手前先查：我要做的事，对应的决策是什么状态？
Get-Content D:\zynq-yolo\ai\coordination\DECISIONS.md

# 2) 若状态是 discussing ⇒ 只能做只读调研、写方案，不得改 src/ build/ board/
# 3) 有了新结论要落实现 ⇒ 先向用户确认裁定 ⇒ 再更新状态 ⇒ 再动手
# 4) 新增讨论项：在 DECISIONS.md 表尾追加一行，状态写 discussing，并注明「不得据以行动」
```
