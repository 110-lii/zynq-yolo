# Session 014 — HDMI/LCD 画面全部打通：三个叠加 bug 的一次定位

## 结论（先给结果）

**两块屏都出画面了。** LCD 与 HDMI 各写一幅 64×64 棋盘格，人眼确认可见。
013 判定的「显示未通过」至此推翻——但 013 的排查结论（AXI、引脚、时钟、时序都不是原因）
是对的，真正的原因在 013 之后的三个叠加缺陷，其中两个直到这一轮才被板上的读数抓出来。

## 三个 bug（每一个单独都足以全黑）

### 1. BRAM 读口 rstb 极性接反 —— 根因，此前从未被怀疑

`system.v:230` 生成的网表：

```verilog
.rstb(rst_pix_peripheral_aresetn)
```

BRAM 的 `rstb` 是**高有效**同步复位，而 `proc_sys_reset` 的 `peripheral_aresetn` 是
**低有效**（名字末尾 `_n`）。正常工作时它是 1 ⇒ 读端口**全程处于复位**，`doutb` 恒为 0。

这解释了 013 里最矛盾的一条观察：PS 侧写 28800 字、读回一致（Port A 走 AXI BRAM Ctrl
自己的 RST，接法正确），而 PL 侧什么都读不到。**写入与读出走的是同一块 BRAM 的两个独立端口，
只有一个端口的复位接错了。**

修法：Port B 不需要复位，`rstb` 直接接 `xlconstant 0`。

### 2. fb_reader 移位方向与取值位相反

```verilog
sr <= {sr[30:0], 1'b0};        // 左移，最低位补 0
pixel_data <= sr[0] ? WHITE : BLACK;   // 却取最低位
```

左移把 bit0 补成 0，每个 32 位字里只有载入后第一拍那一位是真值，其余 31 位恒黑。
`lcd_fb_reader.v` 是同一份代码，同一个 bug ⇒ 两块屏同时黑，这正是 013 里
「两者共用的部分失效」这个观察的落点。

修法：改成右移、按位序输出——bit0 在载入那一拍直接取 `bram_dout[0]`，
之后每拍 `sr <= {1'b0, sr[31:1]}` 并取 `sr[1]`，跨字时接上一字右移 30 次后剩下的 `sr[0]`（bit31）。

### 3. pixel_xpos 的 +2 偏移没在 fb_reader 里补偿

`video_driver.v:103` / `lcd_driver.v:135`：

```verilog
pixel_xpos <= cnt_h + 11'd2 - H_SYNC - H_BACK;
```

而 `data_req` 在 `cnt_h = H_SYNC+H_BACK-2` 时就已经有效 ⇒ `pixel_xpos` 最小值是 **2**，不是 0。
fb_reader 里判断字边界的条件是 `xpos[4:0] == 5'd1`，等的是一个永远不出现的值，
`sr` 一次也没有载入过。

修法：两个 reader 都引入 `wire [10:0] xe = (xpos >= 2) ? xpos - 2 : 0;`，
地址计算与字边界判断全部改用 `xe`。

## 定位过程（这一轮真正起作用的动作）

前四轮都是「读代码 → 猜 → 改 → 重新出片 → 看屏」，全部落空。第五轮改了方法：
**把内部信号用 AXI GPIO 拉回 PS 直接读**。

`lcd_status_top` 增加两个 32 位调试输出：

- `dbg1 = {7'b0, lcd_de, pixel_data}`
- `dbg2 = {10'b0, v_cnt, h_cnt}`

BD 里加双通道 AXI GPIO（`0x41200000`）。第一次读数：

```
d1=0x01101820 de=1 pix=0x101820 | d2=0x000c914f h=335 v=402
d1=0x01101820 de=1 pix=0x101820 | d2=0x00092b15 h=789 v=293
```

**h_cnt、v_cnt 在连续变化** ⇒ 像素时钟在跑、复位已释放、DE 已拉起；
**pixel_data 恒为 `0x101820`（BLACK）**，而当时帧缓存里写的是全白 ⇒
问题被一刀切成「数据侧」，时钟与复位全部排除。

有了这个判据，才能顺着 `bram_dout` 一路查到 BRAM 端口复位。修 rstb 后再读：

```
--- 全白
de=1 pix=0xffffff | h=487 v=397
--- 全黑
de=1 pix=0x101820
```

读写跟随成立，然后才让人眼看屏。

## 被否决的假设（留档，避免重复走）

| 假设 | 否决依据 |
|---|---|
| opt_design 的 BRAM 功耗门控（COOOL gate）掐断读口 | 网表逐颗查：`enb` 是 `xlconstant 1`、`web` 是常量 0，门控只作用在 Port A 的 `wea` |
| MMCM 未锁定导致无时钟 | 板上读回 `h_cnt` 持续变化，像素时钟正常 |
| 33.3 MHz 场频不被屏接受 | 改 25 MHz 后仍黑；根因与频率无关（但 25 MHz 保留，与 oi 一致） |
| `dcm_locked` 悬空致 rst_pix 常复位 | 补齐连接后仍黑；`h_cnt` 证明复位其实是释放的 |
| 屏/线/引脚硬件故障 | 加载 oi 项目 bit，同屏有画面 |

## 纪律（给下一次）

1. **「机器判据全绿」只覆盖它真正走过的路径。** `DISPLAY_BOARD_OK` 读的是 AXI BRAM Ctrl
   的 Port A，从未经过 fb_reader 的 Port B。两个端口是独立的，一个绿不代表另一个活。
2. **盲改四轮是浪费。** 应该在第二版之后就上可读探针，而不是第五版才做。
   板上有 PS，任何内部信号都能通过 AXI GPIO 拉出来，代价只是一次出片。
3. 复位极性这类问题，**看生成的网表比看源码快**。`system.v` 里 `rstb` 接了哪个网络，
   一 grep 就能看出来，比在 BD 图里找连接可靠。
