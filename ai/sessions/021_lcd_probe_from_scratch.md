## 设计口径（写死在代码里，PS 只有一处接口）

帧缓存：每行 `WPR = W/32` 个 32-bit 字，共 `H` 行；**字内 bit0 = 最左像素**；
地址 = `row * WPR + word`。800×480 → 12,000 字；480×272 → 4,080 字。

读侧不用「地址→数据固定几拍」的假设：先把整行读进 `stag_flat`，在**有效行刚结束的那一拍**
一次性并行装进 `line_buf`，显示期只做 1 bit 右移。这样 BRAM 读延迟 1~2 拍都成立。

cfg（AXI GPIO 输出，默认 0）：

| 位 | 含义 |
|---|---|
| [0] | 像素时钟相位：0 = 180°（默认），1 = 0° |
| [1] | 背光：0 = 亮（`lcd_bl = ~cfg[1]`） |
| [3:2] | 纯 PL 图案：0 彩条+外框+刻度+十字+移动块 / 1 全白 / 2 棋盘 / 3 网格 |
| [4] | 1 = 显示 BRAM 帧缓存 |
| [5] | 1 = 480×272 核心，0 = 800×480 核心 |

PS 地址：`0x40000000` 800×480 帧缓存、`0x40010000` 480×272 帧缓存、`0x41200000` ID、
`0x41210000` 时序/tick、`0x41220000` cfg。

| 项目 | 内容 |

| **错在哪**（原始判断） | 第一版读侧写的是「只要不在 DE 就 `line_buf <= stag_flat`」，想靠消隐期反复重装来对齐 |
| **怎么发现**（触发条件） | 写完做时序推演：消隐一开始预取器就把 `stag_flat` 覆盖成下一行，消隐末尾装进去的是「下一行」，整幅会固定偏移一行 |

| **怎么改**（修正动作） | 只在有效行结束的那一拍装一次；`stag_flat` 的预取本来就发生在上一行有效期内，装载时它正好是下一行 |
| **判据**（怎么确认改对了） | 逐周期黄金模型整帧对比（待补；当前只有推演，**不算验证**） |
| **根因归纳** | 行缓存类设计里「缓冲区什么时候是稳定的」必须写成一个明确的时刻，不能靠「消隐期都可以」这种模糊条件 |

`id_toggle` 从「永久 OR」改成最近 256 个样本的滑动窗口，避免上电毛刺永久污染结论。

### 上板复测与根因（2026-10-29）★ 端口 B 把字地址当成了字节地址

**换打法：不再靠照片反推，让 PS 直接读数字。** core 里加一组抓取寄存器
（`dbg_lb0/lbmid/st0/stmid`，`cfg[15:6]` 选面板行），经 3 个 AXI GPIO 暴露：
`0x41230000`=line_buf、`0x41240000`=stag_flat、`0x41250000`={预取次数, 行 DE 拍数}。
配 `lcd_data.py --pattern tag` 的自证图（第 r 行第 w 个字 = `(r<<16) + w`），
一次扫描就能解出「面板第 R 行第 x 个字实际读到的是源图哪个字」。

实测（仪器化 bit `ba36c346…`，16 个行号）全部指向同一个变换：**`bram_dout = mem[bram_addr >> 2]`**。
逐点复核（R = 面板行，j = 该行第 j 个显示字，字地址按 `R*25 + j` 算）：

| R | j | 设计要读的字地址 | 硬件实际读 | 观测值 |
|---|---|---|---|---|
| 0 | 0 | 0 | mem[0] | `00000000` |
| 1 | 0 | 25 | mem[6] | `00000006` |
| 2 | 0 | 50 | mem[12] | `0000000C` |
| 2 | 12 | 62 | mem[15] | `0000000F` |
| 241 | 0 | 6025 | mem[1506] | `003C0006` |
| 241 | 12 | 6037 | mem[1509] | `003C0009` |
| 478 | 0 | 11950 | mem[2987] | `01DE0006` |

照片上的三个怪象因此全部有解：整屏 4 倍放大；每个面板行只看得到该源行最左边的 7 个字；
8 条通栏横线只剩 2 条；最左那根 3px 实心柱被拉成 12px，看着像「坐标轴」。

**根因**：BD 里的 `blk_mem_gen` 被 `axi_bram_ctrl` 的字节写使能接口带成了
`C_USE_BYTE_WEA=1 / C_USE_BYTE_WEB=1 / C_ADDRx_WIDTH=32` —— 这种模式下 `addra/addrb`
都是**字节地址**，IP 内部右移 2 才取字；控制器自己的 `bram_addr_a` 也是 `[15:0]` 字节地址。
读侧却把字地址 `row*WPR + word` 直接接到 `addrb`，于是永远读到 `mem[addr>>2]`。

**为什么此前所有测试都没抓到**：PS 的写和读都走端口 A，两边一起移位，回环
（包括 `readback_bad=0`）必然自洽；而 iverilog 黄金模型把 BRAM 建模成 `mem[bram_addr]`
（字地址），等于替硬件做了一个未经核实的前提。**回环测试证明不了地址口径，
只有「另一侧读到的内容」能。**

**修正（一次出片，三处同改）**：

1. core 内部只算字地址 `bram_wa`，出口 `bram_addr = {bram_wa, 2'b00}`，端口加宽到 16 位；
2. 顶层 `bram_addr_800/480` 同步加宽；Tcl 里把 `CONFIG.Use_Byte_Write_Enable {true}` 显式
   钉死，防止 IP 默认值变化时再次静默翻车；
3. 仿真台改成按真实 IP 口径 `mem[bram_addr >> 2]` 取数（并对越界地址防护）。

**判据**：

- 仿真：64×8、480×272、800×480 三种几何 × BRAM 读延迟 1/2 拍，全部 0 错
  （800×480 累计 1,536,000 px）；把 core 换回旧写法后同一台子报 `errors=720` —— 说明它现在
  抓得住这类错误，而改之前它抓不住。
- 出片：`LCD_PROBE_BD_OK`，WNS **+4.421 ns** / WHS **+0.059 ns**，0 failing endpoints，
  「All user specified timing constraints are met」；bit `39b717de…`、hwh `676237ea…`，
  上传后板端 sha256 与本地一致。
- 上板数字（tag 图，新 bit）：12 个行号全部读回 `(R<<16) + 0`，行中第 12 个字恒为
  `(R<<16) + 0x0C`，`lb == st` 成立，行 DE 拍数恒 **800**；pclk 33.339 MHz；
  h=[0,1054]、v=[0,524]。
- 人眼（**明确判据**）：`split` 图（左半全白 / 右半全黑、最右一列白）上屏后，用户确认
  「**对的**」—— 帧缓存内容确实在驱动这块屏，通路是活的。
- 人眼（口头，证据较弱）：test chart 上屏时用户说「现在完全一致」；但同一批次的两张标尺照片
  拍出来是「白框 + 32px 均匀网格」，与该时刻的读数（`lb0` 在 0/60/240 行为全白、1/61 行只有
  左端 `0x7`）**互相矛盾**，我未能解释这两张照片对应的是哪一帧，**按不可解释现象如实记录，
  不拿它当通过依据**。后续以 `split` 的确认 + 真实图片照片为准。

**两条操作教训（比结论更通用）**：1. **`Overlay()` 每加载一次就重配 PL**：`cfg` 归零、BRAM 内容清零。所以「开第二个进程去读现场」
   这个动作本身就会毁掉现场（我第一次读调试寄存器就撞上了，读回全 0）。正确做法二选一：
   用 `--hold` 让原进程活着，或用**纯 MMIO**（不构造 Overlay）去读 `0x4122xxxx`。
2. **「PS 读回一致」不能证明显示内容**：它只覆盖 AXI 一侧；屏幕到底显示什么，要么人眼、
   要么把要显示的内容抓成寄存器（本例 `dbg_lb0`）。照片反推在光线/透视/拍摄时刻上都不可靠。

另记两条板端事实：ID 采样 `level=0x000000 / toggle=0xFFFFFF` ⇒ 24 根 RGB 在消隐期浮空翻转，
**020 用 ID 判定分辨率的结论不成立**；800×480 由「pclk 33.337 MHz + 纯 PL 图案满屏且几何正确」
确认。板端 `lcd_probe.bit` 曾长期是旧片（sha `1496bc6b…`），已按 sha256 与本地逐字节对齐。

#### 状态面板第一次上屏「字都重叠」—— 写屏版面与读侧行宽不是同一个常量 ★

**现象**：面板写进去后，屏上确实在显示数据，但**相邻几行文字叠在一起**（用户原话「字都重叠了」），
整体看着像「最开始那张糊图」。当时现场读数全部正常：`CFG=0x10`、pclk 33.351 MHz、
`de=800`、`lb==st`，所以不像 RTL 的问题。

**定位过程（三次测量，每次都排除掉一类原因）**：

1. **读侧是否读到 PS 写的那份数据？** 往 `0x40000000`（面板行 240 首字）写 `0x55555555`，
   调试寄存器立刻变成 `0x55555555`；写回原值又变回去 ⇒ **PS 写什么，PL 就读什么**，
   读侧（地址口径、行缓存、移位）到此全部排除。
2. **那份数据本身对不对？** 板上 `0x40000000` 行 240 首字是 `0x7FC00000`，
   而按 800×480 打包面板应为 `0x000FC000`（左侧装饰竖条 = bit14..17）。
   把板上值拿去在**全部候选镜像**（tag/map/pitch/chart/split/status/diag/photo）里逐字搜，
   一个都搜不到 ⇒ 不是「显示了别的图」，是**行的排布被改过**。
3. **谁改的？** 翻 `status_display.py` 的写屏分支：

   ```python
   if args.fb_bram:
       img_hdmi = imgs.get((1280, 720))
       if img_hdmi is None:
           img_hdmi = render(st, 1280, 720, ctx)      # ← 不看 --size，永远 1280x720
       mode = write_image(img_hdmi, int(args.fb_bram, 0), 1280, 720)
   ```

   `--fb-bram` 一律按 **1280×720（40 字/行）** 打包；LCD 读侧按 **800×480（25 字/行）** 取数。
   每往下一行，源图多走 40 字、面板只走 25 字，**每行错开 15 个字（480 px）**，
   于是相邻 2~3 行的内容被甩到同一行上 —— 就是「字叠在一起」。
   另外 1280×720 是 28,800 字，越界 16,800 字直接压进 `0x40010000`（480×272 那块 BRAM，
   事后读回有 813 个非零字），属于**写坏第二块内存**的连带损伤。

**修正**：`status_display.py` 新增 `_bram_layout(sizes)`，`--fb-bram` 的版面跟着 `--size` 走
（只请求一个受支持尺寸时就用它，同时请求两种才退回 HDMI 1280×720 的老行为）；
令牌改成 `STATUS_DISPLAY_BRAM <base> layout=WxH words=N via ...`，**版面写错时从日志就能看出来**；
`--selftest` 增加三条版面映射断言 + 「800×480 必须打包成 12000 字」。

**判据**：

- 板端令牌：`layout=800x480 words=12000`（此前是 `layout=1280x720 words=28800`）。
- 12 个抽查行的 `BRAM 写进去的字 == PL 读侧送屏的字` 全部相等，`de=800`；
  第 60/90/240/300/360 行首字均为 `0x000FC000`，与本地 800×480 打包逐字一致。
- **人眼**：用户确认「**现在好了**」 —— 状态面板（8 项信息）第一次真正上屏通过。

**根因归纳**：同一块内存的两端各有一个「行宽」常量（写侧 `w//32`、读侧 `WPR`），
它们不一致时**双方都不会报错**：读侧只是老老实实按自己的行宽取数。
所以「行宽/版式」必须和「地址口径」一样，做成**一处定义、两端共验**，并且**打进日志令牌**。

#### 1bpp 屏的小字：字号与描边

用户反馈底栏（源文件/后端那行）与最左标签列「字太小、模糊」。原因是抗锯齿灰字二值化
（>128 记白）后，细笔画被整段掉光。改法（都在 `render()`/`Painter.flush()` 里）：

- 左标签列 16 → 18 px，标签列宽 150 → 162，最小字号 10 → 12；
- 底栏 13 → 16 px，颜色提亮到 `(208,214,226)`，并加粗；
- `bold` 在 PIL 后端真正生效：**≤20 px 的粗体用 1 px 描边**（`stroke_width=1`，
  同色填充），让细笔画在二值化后仍然连得上。

## 结论与沉淀

**可用结论：**

- 屏是 **800×480**，pclk 33.333 MHz（实测 33.337/33.339 MHz），DE 模式、HS/VS 恒高；
  纯 PL 图案满屏、几何正确 —— 时序/引脚/前向时钟这一层到此为止可算通过。
- 帧缓存读侧（预取整行 + 行末一次性装载 + 移位输出）在仿真里逐像素正确，上板后
  `lb/st/DE 拍数` 三条数字判据也对得上；**剩下只差人眼**。
- 这条最值钱：**「写进去再读回来一致」不能证明地址口径**。PS 与 PL 若各错一半、
  方向相反，回环永远自洽。要抓它，必须让另一侧（PL）读、并让内容自己带坐标
  （`(row<<16)+word` 这种自证图），或者让仿真台按真实 IP 的地址语义建模。
- 同理第二次：**照片反推不如寄存器直读**。加 5 个调试寄存器（3 个 GPIO）就把
  「4 倍放大 + 6 字偏移」这种鬼现象换算成了 16 个整数，根因一次定位。
- 状态面板（8 项信息）到 2026-10-29 已在 800×480 屏上**人眼通过**（「现在好了」）。
  它暴露出第二类「口径不一致」：**写侧行宽 `w//32` 与读侧 `WPR` 是两个独立常量**，
  1280×720 的版面写进 800×480 的 BRAM 不会报错，只会让每行错开 15 个字 ——
  屏上表现为「字叠在一起」，且顺带越界写坏第二块 BRAM。
  修法与验收：版式跟着 `--size` 走、令牌打印 `layout=/words=`、自检断言打包字数。
