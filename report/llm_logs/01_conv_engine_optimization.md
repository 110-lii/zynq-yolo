## 1. 任务与提示词（逐字）

会话 005 的起点是用户一句：

```
现在继续昨天的任务
```

当时的板端现状：`conv_engine` 整网 **41.4 s/帧**，59 层 PL 卷积约 33.35 s，
PS 首层 5.75 s；单层读吞吐只有 **10–22 MB/s**，与层形状无关。

模型给出的第一版假设是“装载字节数是主因”：旧代码恒按 `K_MAX=3` 行、`LB_W_MAX=82`
列装载，**596 MB/帧**；按 `kh<K` + 运行期列界后降到 **77 MB/帧**，预测整网可到 0.94 s。

用户随后逐轮批准：


## 2. 模型回答与实测（按轮）

| 轮次 | 改动 | 模型预期 | 实测 | 判断 |
|---|---|---|---|---|
| 1 | `kh<K` 行守卫、运行期 `ncol`、`num_read_outstanding=16`、`max_read_burst_length=64` | 整网 8.4 s → 0.94 s（约 8×） | **41.4 → 34.1 s**；单层 `k1s1_smallw` 输入 246→10 B，时间只 7.83→5.93 ms | **原假设被推翻** |
| 2 | 权重装载展平 + `PIPELINE II=1`，`wbuf` 一维化 | 权重装载是大头 | **34.1 → 25.7 s**（conv 31.9→23.4 s），scores 完全一致 | 部分采纳 |
| 3 | PS 首层 `int8_conv` 改 float32 精确累加（`2·taps·255·128 < 2^24` 时等价） | 省 5.75 s 中的大部分 | **25.7 → 20.8 s**（conv 23.4→18.5 s），逐位相等 | 采纳 |

三次改动后，整网 **41.4 → 20.8 s/帧（1.99×）**，检测 scores 逐位不变。
但模型明确写出：**仍未达到 5–8 FPS**，剩余差距不能用“总字节”解释。

## 3. 自我纠错轨迹

| 项 | 内容 |
|---|---|
| **错在哪** | 第一轮认定“装载字节数是主因”，按 596→77 MB/帧 预测 8× 加速。 |
| **怎么发现** | 第一版上板只从 41.4 降到 34.1 s；单层输入从 246 B 砍到 10 B，时间只降 1.3×。 |
| **证据** | `data/results/stream_client_v5_fb_ld.json`（34149.5 ms）、`board/logs/board_layer_test_20211118_0633.md`（`k1s1_smallw` 5,931,548 ns）、csynth 中权重循环没有独立流水条目。 |
| **怎么改** | 不再按“总字节”建模，改为按 **ci-tile 拍数**分解：`k1s1_smallw` 772 拍 = 输入 10 + 权重 ~720 + 卷积 40 ⇒ 权重散读是主要串行点。 |
| **判据** | 单层 `k1s1_smallw` 5.93→3.62 ms；整网 34.1→25.7 s；三次检测 scores 完全一致；csynth 权重循环 `II=1, latency 84 / 72 triples`。 |
| **根因归纳** | HLS 只对**显式标注 `PIPELINE` 的循环**做流水；展开在 `ci` 循环体里的散装标量读各自吃满存储延迟。`csynth.rpt` 里“没有独立循环条目”本身就是“这段没被流水”的信号。 |

## 4. 第二轮：字节事务 → 32-bit 字（会话 008）

会话 008 把问题定位到代码级，而不是继续调参：

1. `in` / `w` 是 `ap_uint<8>*` / `ap_int<8>*` ⇒ m_axi 事务粒度 1 字节；
2. 装载循环里 `ok ? in[addr] : zp` 把读地址挂在条件上 ⇒ 无法合并突发；
3. `w` 端口没有 `num_read_outstanding` / `max_read_burst_length`；
4. 权重按 `[co][ci][9]` 散读，每个 ci 要 72 次独立单字节读，实测 ~720 拍/ci。

改法：顶层 `in`→`ap_uint<32>*`、`w`→`ap_int<32>*`（字节布局不变，PS 侧无需改数据）；
输入按整字覆盖窗口、读地址连续且无条件；K=1 读 1 字、K≥2 读 3 字拼 96-bit；
尾块“下标钳位 → 读 → 数据清零”；读口 32 outstanding、64 beat 突发。

验证：g++ 直跑 6 个用例 **6/6 `TB_CONV_OK`**；上板后整网 **20.8 → 9.63 s/帧**，
conv **8.13 s**，其他 **1.45 s**（`board/logs/board_stream_new_20261022.md`）。
资源：LUT 23,552 / FF 21,991 / DSP 172（78.18 %）/ BRAM 12.5，WNS **+1.350 ns @83.33 MHz**。

## 5. 结论与教训

- **可用结论**：PL 引擎逐层正确（6/6 bit-exact），优化后 9.63 s/帧；但 78 % DSP
  只换来 0.10 FPS，因此退出主线（D017），只作技术验证资产。
- **可复用教训**：性能排查先看 `csynth.rpt` 的循环表，再看总字节；散装标量读、
  条件读、字节事务是 HLS + AXI 的三个隐藏串行点。
- **未决**：装载/计算重叠（DATAFLOW/ping-pong）、拆 bundle、消除 `co0` 重复读，
  在 9.63 s 版本上仍未做；这些是后续若重启 PL 路线的第一优先级。
