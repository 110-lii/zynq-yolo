# 05 · 显示通路的两次推倒重来：从「读回通过」到「屏上是乱码」

> 原始出处：`ai/sessions/012`–`022`（2026-10-27 – 2026-10-30）。
> 对应设计报告 §2.9 / §2.10 / §8 第 8、10、11 条；代码落点与自检命令见文末。
> 这一篇记录的是**失败与纠错**，不是成果清单：显示是本项目返工次数最多的部分。

## 1. 用户指令（逐字）

2026-10-29：

```
现在你来做lcd的显示数据，不要相信已经存在的东西，他们现在都是错的
```

2026-10-27（D026 的来源）：

```
现在还需要hdmi输出带框的画面
```

两条指令的共同点：**用户不接受「寄存器读回一致」作为「显示正确」的证据**。
这直接决定了本项目后来的判据口径（§5）。

## 2. 错误链：三次「以为好了」

### 2.1 第一次：读回全对，屏幕全黑

- 现象：`DISPLAY_BOARD_OK`（28,800 / 12,000 字逐字读回一致），HDMI 只亮背光、LCD 全黑（`ai/sessions/013`）。
- 当时排除的：AXI/BRAM 通路、TMDS 四引脚（对 AMD 官方 pinout）、50 MHz 晶振、时序收敛。
- 真正根因（014 才抓到，且是**三个叠加缺陷**）：
  1. BRAM 读口 `rstb` 极性接反 —— `peripheral_aresetn`（低有效）直连高有效的 `rstb`，
     读口全程复位、`doutb` 恒 0；
  2. `fb_reader` 左移却取 `sr[0]`（位序反）；
  3. `pixel_xpos` 从 2 起算，与字边界差 1 拍。
- **教训一**：三个 bug 里只有一个能让通路「完全不动」；另外两个只在**特定列**出错。
  因此「有些像素对」不等于「装置对」——必须**整场逐像素**比，不能抽样。

### 2.2 第二次：修完之后，屏上是乱码

- 现象：014 人眼确认棋盘格可见；017 复测同一块 LCD，**帧缓存读回 100% 正确，屏上却是
  「灰长条 / 大小不一的渐变方块」**，且随 BD 重写变化。
- 判断过程：先怀疑队列版读侧（017），写在仿真里跑整场后证伪（018）；真正原因是
  **`pixel_data` 是寄存器输出，而 `video_driver` 用组合选通 `video_rgb = video_de ? pixel_data : 0`**
  ⇒ 每行第 0 列必然读到消隐期的黑，且「地址到数据恰好 1 拍」的假设不成立。
- 修法：改成**预取移位寄存器**（消隐期持续装载本行 Word0；显示期每位右移，末位前 32 拍发下一字地址），
  LCD 与 HDMI 同构（018/019）。整场仿真 0 错。
- **教训二**：仿真必须跑**整场**（480×800 / 720×1280）而不是几十个像素；
  018 用 iverilog 把整场跑出来之后，「队列版 vs 移位版」之争当场结束。

### 2.3 第三次：几何全错 —— 不是读侧，是像素时钟

- 现象：读侧已对，画面仍是「几何全错」（016）。
- 根因：像素时钟 25 MHz + 1056×525 ⇒ **45.1 Hz**，而这块屏（ST7262）按 **60 Hz** 设计。
- 修法：独立 MMCM 出 33.333 MHz（板上实测 33.356 MHz、60.13 Hz）。
- **教训三**：「数据对」与「时序对」是两件事；显示类问题要先量**像素时钟与帧率**，再查数据通路。

## 3. 第二次推倒重来：4bpp 与调色板（021）

用户明确要求「不要相信已经存在的东西」之后，重做范围被定为**整条通路**（数据格式 + 读侧 +
时序 + RGB 输出），且**分辨率先实测再定**，不许假设 800×480。

关键取舍（`ai/sessions/021`）：

1. **一块 bitstream 跑两个分辨率核心**（800×480@33.333 MHz、480×272@9.000 MHz），
   PS 写 `cfg[5]` 切换；`cfg[4]=0` 时输出纯 PL 图案、不碰 BRAM。这样「屏到底哪个分辨率」
   「相位对不对」一次上板就能 A/B，不必反复出片（出片十分钟级，且本机易 OOM）。
2. **1bpp → 4bpp / 16 色**：8 像素/字，**最低 4 位是最左像素**；800 像素 = 100 字/行，
   480×100 = 48,000 图像字 + 16 个调色板字（192 KB，AXI 段必须开 256 K）。
3. **调色板每场垂直消隐装载 16×24-bit** ⇒ 改配色不需要重出片；16 色 = 6 个界面色 + 10 个球衣色，
   球衣色的 RGB 由 `classify_players.PALETTE_REF` 的名字换算 ⇒ **屏上所见即分类器判色的参考色**。
4. **赛前 UI 用同一份 schema**（`zynq-yolo/match-config/2`）：屏上输入的数据下游能直接用，
   确认时复用 `match_setup._validate`（两队同色直接拒绝）。

## 4. 自我纠错：四条被证据推翻的判断

| 当时的判断 | 怎么被推翻 | 证据 |
|---|---|---|
| 「读回一致 ⇒ 显示通过」 | 013：读回全对、屏全黑 | `ai/sessions/013` |
| 「队列版读侧是根因」 | 018：整场仿真证明队列/移位都不是根因，是打拍与选通 | `ai/sessions/018` |
| 「25 MHz 够用」 | 016：1056×525@25 MHz = 45.1 Hz，屏按 60 Hz 设计 | `ai/sessions/016` |
| 「BRAM 地址就是字地址」 | 021：`Blk_mem_gen` 带字节写使能时 `addra` 是**字节地址**（硬件读 `mem[addr>>2]`），RTL 必须驱动 `{word_addr,2'b00}` | `ai/sessions/021`、`lcd_probe_core.v` 文件头 |

另外两条工具侧的纠错，属于「证据采集方式本身会制造错误」：

- **不要用「试连一下端口」探活**：`pc_dashboard --listen` 会把空连接当成一次会话结束而后退，
  探活反而把要用的服务弄死 ⇒ 改成固定等待 + 检查进程是否还活着（`ai/sessions/022`）。
- **`result_stream` 默认从 EOF 读**：文件写完再传会一行也发不出去 ⇒ 流程里必须带 `--from-start`，
  并给子进程设超时（超时判 FAIL，不抛异常）。

## 5. 沉淀成纪律：判据分两级

这是本项目对「什么叫做完」的唯一回答，已写进报告 §2.9 与 `docs/system_status.md`：

- `BRAM_OK`：帧缓存写得进、读得回、扫描范围/速率对 —— **机器可判**；
- `VISUAL_OK`：屏幕上真的看到、且内容与风格正确 —— **只能人眼判**。

两者**不得互相顶替**，也不得把「已出片」「已上板读到数」写成「已显示」。
在此基础上，上板验收固定三级阶梯：**white → chess → panel**（另加 `under` 行欠载计数）。

## 6. D026：从「不做视频输出」到「必须带框」

- 背景：D018 当时把「视频环出/OSD」列为不做；2026-10-27 用户要求 HDMI 输出带框画面，登记 **D026**。
- 结构：PS 在 DDR 画 32bpp 帧，PL `fb_scanout` 经 `S_AXI_HP0` 读成像素流（见报告 §2.10）。
- 两个必须记住的硬约束：
  1. HP0 的 ACLK 必须与 pclk 74.25 MHz **同源**（读主机内没有跨时钟桥）；
  2. Zynq-7000 的 HP 是 **AXI3**，AXI4 主机必须过 `smartconnect`；且 PS 的 `M_AXI_GP0`(83.33)
     与 74.25 之间的准静态配置总线若不隔离，会被当同步路径，实测 **WNS −8.001 ns / 166 端点**
     ⇒ 必须插 `axi_clock_converter`。
- 证据边界：`TB_FB_SCANOUT_OK`（2048 像素逐点 0 错）与主机侧 OSD 出图只证明**渲染器**正确；
  出图用的是**演示给定坐标**，不等于检测器给的框对。板上的 `under` 与「框落在真人身上」都还没看。
