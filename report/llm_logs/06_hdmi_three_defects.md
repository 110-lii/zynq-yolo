# 06 · HDMI 从「一片全绿」到「六屏全对」：三处叠加缺陷与两轮上板

> 原始出处：`ai/sessions/022_hdmi_osd_full_flow.md` §7.13–§7.22（2026-10-30 – 10-31）；
> 汇总口径见 `docs/system_status.md` 的「10-31 上板两轮」与
> `report/design_report.md` §2.10 / §8 第 8、12 条。
> 这一篇记录的是**判据如何被重新定义**，不是「又修了一个 bug」。

## 1. 用户指令（逐字）

2026-10-27（D026 的来源）：

```
现在还需要hdmi输出带框的画面
```

2026-10-29（显示返工的起点）：

```
现在你来做lcd的显示数据，不要相信已经存在的东西，他们现在都是错的
```

两条指令的共同点：**用户不接受「读回一致」作为「显示正确」的证据**。
10-31 的 HDMI 收尾，本质上就是把这句要求落实到每一层判据上。

## 2. 错误链：机器全绿，屏上全错

### 2.1 第一层：地址段没分配，读请求根本没有从设备

`bd_flow_system.tcl` 漏了 `hdmi_video_0/m_axi` 的 DDR 地址段。构建只留下一条
`CRITICAL WARNING [BD 41-1356]`，实现与时序全过；上板后 `frames` 60 帧/s、
`under=0`、cfg 写读闭环全绿，**屏上却一个颜色都不变**。

- 错在哪：把「时序收敛 + 寄存器能写」当成「数据通路通」。
- 怎么发现：cfg 写进去、状态读回来都正常，但帧号累加与像素和都不随画面变化。
- 怎么改：显式 `assign_bd_address`，并在构建期断言分配不到就 `FLOW_SYSTEM_BD_FAIL`。
- 判据：`FLOW_SYSTEM_BD_OK` 必须包含地址表逐条对拍。

### 2.2 第二层：行推进条件永远不成立，每行都读第 0 条行缓存

`fb_scanout` 写成：

```verilog
if (de && (local_x == width_use - 1))  // 真实 local_x 最大 1277
```

`width_use=1280`，而 `video_driver` 的 `de` 期 `local_x` 最大 1277 ⇒ 条件永不成立
⇒ **整屏每一行都读同一条行缓存**。表现是「竖条对、横条和文字全丢」，
而 `st_under` 对这个缺陷**永远报 0**。

- 错在哪：用「数 de 拍」推相位，而不是用 `video_driver` 自己保证的场计数。
- 怎么改：`cur_line = ypos - 1`（`ypos` 由 `video_driver` 产生），不再依赖推出来的相位。
  前两版（等式判据、脉冲计数）都栽在同一类问题上，这是第三次、也是唯一不靠推的写法。

### 2.3 第三层：cfg 写到了错误的总线域

`flow_system.bit` 里 `0x41200000`（HDMI cfg）写不进去，读回的是 `0x41210000`
（状态 GPIO）的值 —— 配置从未进过 PL。把 cfg 挪到外层 `axi_smc`（FCLK 域，
与 LCD 已验证可写的 GPIO 同一条总线），状态 GPIO 留在 pclk 域。

- 错在哪：以为「地址相同就通」，没有核对 BD 里两个 GPIO 分别挂在哪个时钟域。
- 判据：cfg 写入后必须读回同一个值，且 PL 侧状态要随之变化。

## 3. 自我纠错：三次判断被证据推翻

| 当时的判断 | 怎么被推翻 | 证据 |
|---|---|---|
| 「帧缓存 `cacheable=True`，加 `Buffer.flush()` 就好」 | 刷完仍然纯白；`flush()` 不是根因 | `ai/sessions/022` §7.13 |
| 「`under=0` 说明取数没问题」 | 读回全零时 `under` 照样是 0 | `docs/system_status.md` |
| 「每行都读靠前的行」（由累加和反解） | VRAMP 的 `0x3ACB0000` 要求 `1280·S ≡ 15051 (mod 65536)`，左边恒被 256 整除 ⇒ **无解**，模型不完整 | `ai/sessions/022` §7.16 |

第三条尤其重要：解析模型互相矛盾时，**不要再靠推理**，改做能唯一反解的直接测量 ——
整幅图只让源行 r 白，`sum = count·1280·0x00FFFFFF (mod 2^32)`，`0x00FFFFFF` 与 `2^32`
互素 ⇒ `count` 唯一；列同理。先在 `tb_hdmi_scanout_sys` 的 `+ROW=`/`+COL=` 模式里
对真 RTL 跑 8/8（含「列 0 显示 3 次、列 1279 显示 0 次」两个边界），
`CHECKED=1843200 ERRS=0`，再上板。

## 4. 两轮上板：把「吞吐」与「对齐」分开

### 4.1 第一轮（旧 bit，12:07）：钉死取数吞吐不足

探针结果：行号 Σ=181,248（应 258,840，整体偏移 −107.77 行）、源行 716–719 完全没显示、
每列只显示一半、`under` 一直是 0。

根因：每行 20 个突发，每个都等数据全回；一行只有 1650 pclk，延迟一超 18 拍就永远追不上。
改法：请求/写入游标解耦 + 4 个突发在飞，`BURST` 64→255。

### 4.2 第二轮（12:52 bit）：机器全绿，人眼发现「右移 2 像素」

机器判据：Σ=258,840 ✓、每个源行恰好 1 次（含 719）✓、源列 0 三次 ✓、VRAMP 累加和
MATCH ✓、`under=0`。人眼：**黑横条没了、画面不跳了**，但整幅图右移 2 像素、
最左 3 列重复源列 0、源列 1278/1279 永不显示。

根因：`video_driver` 的 `xpos` 在 de 拍上取 **C+1**（不是旧注释写的 0…1279），
同步 BRAM 读要求读地址**就是 `xpos`**，不能减 2。改后 13:37 新 bit，
WNS 4.184 ns，`SIM_PASS 12/12`。

### 4.3 人眼终验（13:50–13:56）

部署 13:37 片后，用户当场确认六屏「全对」：

- EDGES：左边缘纯白、右边缘纯红、绿方块居中；
- HBANDS / VBANDS：8 条横带/竖带顺序与厚度正确、无黑横条、不跳；
- GRID：45 条横线 + 80 条竖线一条不少；
- MOTION：运动方块无撕裂；
- MARKERS：三色块贴边、不外溢。

⇒ 当时记为 **`HDMI_VISUAL_OK`**，证据 `data/results/hdmi_visual_ok.json`（绑定 bit 的
sha256 `ad628200…104a`）。随后在同一片 overlay 上跑真视频环出：
`HDMI_VIDEO_OK` 25 帧 `under=0`（机器级）。

> **⚠️ 追记（同日 20:23，本篇的第二个自我纠错）**：上面这个 `HDMI_VISUAL_OK` **已撤回**。
> 同一片 bit 在 19:24 的新片上 19:27 探针 28/28 `OK`、19:50 前后用户确认「现在可以了」，
> **20:23 再测又变成 `px ≈ c + 437`**，用户同步报「又变成之前那样」。今天是第三次测量，
> 恒定 `+313` 列（21 源列 × 7 行一致，`sum=1`）。⇒ 这是**间歇性**缺陷，`k` 随运行相位变化
> （425/399/437/440/441，也出现过 0）。本节其余三处缺陷（地址段、行推进、cfg 总线域）
> 的修复仍然成立；**只有「六屏人眼 ⇒ 通路可用」这一步结论不成立**。
> 证据文件已改为 `HDMI_VISUAL_RETRACTED`；演示通道改用 `tools/video_back.py`（网口回传）。

## 5. 沉淀成纪律

1. **判据必须约束输出本身**：`frames`、`under`、读回一致都不等于画面正确；
   静态图要用「源行/源列各显示恰好一次」这类可反解的判据。
2. **解析模型冲突时改用直接测量**：单行/单列探针比继续解方程更快、更硬。
3. **机器判据与人眼判据分开登记**：`BRAM_OK` / `VISUAL_OK` 两级，不互相顶替。
4. **证据绑定到片**：`hdmi_visual_ok.json` 记 sha256、WNS、六屏现象与「不覆盖什么」，
   换片即失效。
5. **诊断代码当场删**：016 的地址配色诊断曾留在最终 RTL 里，导致整屏彩条；
   本轮所有探针只进 `build/`，不进 `src/`。
