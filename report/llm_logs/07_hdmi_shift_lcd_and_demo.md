# 07 · 从「画面又错位了」到「一条命令演示」：HDMI 平移的定量、LCD 面板与收尾判据

> 原始出处：`ai/sessions/027_event_possession_on_clip.md` 轮次 10–11（2026-11-01）；
> 汇总口径见 `docs/system_status.md` 的「HDMI 行内平移（D031）」与
> `report/design_report.md` §2.10 / §4 的「2026-11-01 优化前后对照」。
> 这一篇记录三件事：**一个一直读错的寄存器地址**、**把间歇缺陷变成可测量的量**、
> **演示收尾判据从「进程在不在」改成「进程的状态位」**。

三条要求合起来是一件事：**交付形态**。不是「功能有没有」，而是「现场能不能一条命令跑出
评委看得懂的东西，且屏上不出错」。最后一句「现在可以了吗」我们没有用旧日志回答，
而是**重跑了一遍整段**（见 §5）。

## 2. 错误链一：读错了两个月的调试地址

### 2.1 症状

HDMI 环出的整行错位反复出现，但每次测出来的偏移量都不一样（0 / 399 / 425 / 437 / 440 / 441）。
想用「状态调试通道」看扫描进度时，读 `0x41290000` 永远得到 `{frames, under}` ——
我们把它解释成「st_dbg 恰好等于帧计数」，甚至据此写过几条结论。

- 错在哪：**没有核对地址解码**。`0x41290000` 根本没被例化，读请求被地址解码到了 status GPIO 上。
- 怎么发现：同一时刻读 `0x41290000` 与 `0x41210000` 得到完全相同的两个字，且读后 `under` 计数会变。
- 怎么改：诊断一律走 `0x41210008`（status 通道 2，`cfg_pack[31:29]` 选择器），
  并把「`0x41290000` 是坏地址」写进 RTL 注释与文档。
- 判据：同一物理量用两条路径读，必须互相印证；单点读数不算证据。

### 2.2 自我纠错留档

> **错在哪**：把「能读到一个像样的数」当成「读到了正确的东西」。
> **证据**：路径 `hdmi_video_top.v:141–155` 的选择器定义；两次读数比对。
> **教训**：诊断通道本身也要被验证 —— 用一个已知答案的输入（单列探针）去反解它。

## 3. 错误链二：间歇缺陷 → 可测量的量

### 3.1 定量

用「源图只让第 j 列 = 1，读回位置加权和」的单列探针（`pos = 720×(屏列+1)`）扫了 47 个点：

- 全部满足 **屏幕列 = 源列 + K**，K = 414；接缝在源 866 → 屏 0，连测 20 次不漂；
- 换一次起管线，K = 415。

⇒ 它是**纯循环平移**（不是丢点、不是重复、不是行错位），K 恒定但**跨运行会变**。

### 3.2 修法

`hdmi_video.HdmiVideoOut` 增加三个方法：

| 方法 | 作用 |
|---|---|
| `calibrate_shift()` | 5 个探针列求 K；探针互相矛盾时返回 0（宁可不补正也不乱补） |
| `_rotate_into()` | 写帧缓存前按 `buf[:, i] = src[:, (i+K) mod W]` 搬列 |
| `verify_shift()` | 补正后**再探一次**，返回最坏的有符号残余量（0 = 逐列恒等） |

`board_pipeline` 起管线时调用一次，日志判据 **`HDMI_ALIGN shift=415 residue=0`**。

### 3.3 自我纠错留档

> **错在哪（第一次实现）**：把补偿方向写反了（`arange − shift`），并且「验证」时写的是
> **未经补正的原图**，于是 `verify` 永远返回失败。两处错误互相掩盖，看起来像「硬件还在变」。
> **怎么发现**：在主机侧把 `np.take(tmp, ix, axis=1)` 与 `np.roll(src, −K, axis=1)` 逐位比对，
> 才发现方向反了；再检查 `verify` 的调用路径，发现它绕过补正。
> **怎么改**：方向改为 `arange + shift`；`verify_shift(apply_shift=True)` 走补正后的真实路径。
> **判据**：任何「验证」都必须走**被测系统真实的那条路**，不能另开一条捷径。

## 4. 错误链三：演示收尾——「僵尸」不是「还在跑」

### 4.1 症状

一条命令演示跑完推流后，日志停在 `PUSH 等板端算完`：

```
BOARD_PIPELINE_WAIT 61s  BOARD_PIPELINE_ALIVE pid=2126 pidfile_pid=2126 alive=True
…
BOARD_PIPELINE_WAIT 548s …                                   ← 板端其实 20 秒就结束了
```

而板端日志早就写了 `PIPELINE_OK frames=25` 与结果文件。

### 4.2 根因

两条，都在上位机的判据里，不在板子：

1. 事件管线是 Jupyter kernel 用 `Popen` 起的**子进程**，kernel **从不 `wait()`**；
   进程退出后变成 `/proc/<pid>` 里状态 `Z` 的**僵尸**，`os.path.exists()` 恒为真；
2. `/tmp/pc_event.pid` 只有一份，**连跑两次**时后一个覆盖前一个，第一次的等待盯上了别人的 pid
   （实测日志里出现 `pid=1720 alive=True` 而板上根本没有 1720 这个进程）。

### 4.3 修法

- 判活改读 `/proc/<pid>/stat` 的**状态位**（`Z` = 结束），日志多打一列 `state=S|Z`；
- 起管线前 `_reap()` 回收本 kernel 名下的僵尸；
- pidfile 上那条**还活着**就先 `SIGTERM` 再起新的（`BOARD_PIPELINE_BUSY pid=N stopped`），
  并清掉 `/tmp/hdmi_preview.active`；
- 等待与收尾都只认**自己这次起的 pid**。

### 4.4 自我纠错留档

> **错在哪**：把「`abandoned` 的进程仍在 `/proc`」当成「它在跑」，并且把超时当作「板子慢」，
> 于是把超时从 300 s 放宽到 1200 s —— **放宽超时掩盖了判据错误**。
> **怎么发现**：板端日志时间戳与上位机等待时长对不上；`ps` 里没有那个 pid。
> **教训**：超时放宽之前先问「这个判定条件本身对不对」。

## 6. 仍然不成立的结论（边界）

- **`HDMI_VISUAL_OK` 不记**：`residue=0` 只证明「列映射恒等、行号对得上」，不证明屏上观感；
- K 在一次演示途中是否会变，**没有观测到也没有防御**；
- 第 167 帧起球跟丢，之后是外推值，不采信；
- 事件模式板端约 1 fps，端到端整段 8–10 分钟，不能称「实时」。
