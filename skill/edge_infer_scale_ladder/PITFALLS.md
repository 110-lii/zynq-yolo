# PITFALLS —— 输入尺度分档实验的坑

> 每条按「触发条件 → 现象 → 排查步骤 → 修复」写。全部来自 `ai/sessions/029` 的真实过程。

## P1 拿 640 模型喂 320：召回精确为 0

- **触发**：同一份权重只导出了一个边长，评测时把 `size=320` 传给它。
- **现象**：squash / letterbox 两种预处理都得到 `召回=0.000`，整齐得可疑；日志里是
  `EXTRACT_FAIL` / `INPUT_FAIL`，不是「检不到」。
- **排查**：查看 `model.ncnn.param` 首行后的 `Input ... 2=640 3=640`；确认导出尺寸。
- **修复**：按边长分别导出（`person_w05_{320,480,640}`），文件名带尺寸，
  运行时尺寸不符直接报错，不静默降级。

## P2 用训练框架的 mAP 代替部署路径

- **触发**：直接引用 `val mAP50=0.841` 作为「模型在这块板上能到多少」。
- **现象**：mAP 漂亮，部署召回只有 0.18；解码、NMS、输入尺度任一不同都会造成差距。
- **排查**：用 `board_detect.detect()` 的真实代码跑同一批图，再与板端替身对拍。
- **修复**：评测统一走部署路径；mAP 只用于训练阶段选权重。

## P3 squash 与 letterbox 混用，结论反转

- **触发**：训练时用 letterbox，评测时用 squash（或反过来）。
- **现象**：预处理「优化」后指标反而下降，误以为方案无效。
- **排查**：核对训练脚本的 resize 与评测脚本的 resize 是否是同一套参数。
- **修复**：把预处理视为模型的输入契约，写进 `detect()` 的 docstring；对照实验同时保留 `--no-letterbox` 开关。

## P4 逆变换把网络坐标当原图坐标

- **触发**：手写自检期望值，直觉认为「720 的一半是 360」。
- **现象**：自检 FAIL：`squash 逆变换 y=360 202.5`。
- **排查**：分清网络坐标（0–319）与原图坐标（0–719）。
- **修复**：用能整除的数写期望值，并同时断言正反两个方向（本队 9 项检查）。

## P5 只测一个边长，把 letterbox 的收益算给「分辨率」

- **触发**：只对比「旧模型 320 squash」与「新模型 640 letterbox」。
- **现象**：涨幅 3.3× 被整体归因于「分辨率提高」，下一题照抄就失效。
- **排查**：固定权重、只改边长；再固定边长、只改预处理。
- **修复**：2×N 矩阵；本队结论是 letterbox 贡献零成本 1.45×（micro 0.326→0.474），边长收益依赖权重是否在该尺度训练过。

## P6 忘了「模型 / 预处理 / 调用参数」三处一致

- **触发**：三处分别在三个文件里，没有任何地方强制相等。
- **现象**：不报错，只表现为精度归零或莫名下降。
- **排查**：打印一次实际输入尺寸、实际模型路径、实际预处理分支。
- **修复**：文件名带尺寸 + 运行时校验 + 自检脚本覆盖三种组合。

## P7 拿 PC 结果当板端结论

- **触发**：PC 上跑完矩阵就直接在报告里写「板上更快/更准」。
- **现象**：板端 `INFER_MS` 未测，帧率代价未知；本队因此没有更换默认模型。
- **排查**：板子在线时补测三档耗时；离线时明确写「未测」。
- **修复**：召回与耗时分开登记，报告里分别标注证据级别。
